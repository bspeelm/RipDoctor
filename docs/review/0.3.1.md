# 0.3.1 — the import answers every question

Tagged from `main`. Two commits since 0.3.0.

## What changed

Three faults in the import, found by a record the catalogue does not describe.

beets asks a second question when the album is already in the library, and only
the first was ever answered; the question reached end of input and the failure
was reported as a track count rather than as what it was. The acknowledgement
the dialog collected for that case never left the browser. And an emptied
release id fell back to the release in the spec, which a first pass always
writes — so the no-catalogue path added in ADR-053's predecessor had been
unreachable for almost every record since it shipped.

Decision: ADR-054.

## Load-bearing surfaces touched

| surface | what changed | the gate on it |
|---|---|---|
| **Executes external processes** | what is piped to the importer's matcher: every answer it can ask for, chosen rather than assumed | the bytes are asserted per choice, and the test seam now records what was piped so the assertion is possible at all |

No change to what writes where, what deletes, or how bytes enter the machine.

## What was executed

- `make check`: format, lint, types, 1081 tests, budgets.
- CI on 3.11, 3.12 and 3.13 green. The branch was brought up to date and the
  checks re-run before merging; the ruleset requires it.
- **The record that found the faults, carried through on the deployed build.**
  Fourteen cut tracks, a catalogue that describes twelve and in a different
  running order. Imported with the catalogue ignored: fourteen rows in the
  library, numbered as the pressing plays, nothing left in review.

## What was not verified

- **Two of the three duplicate answers.** "Replace" is what the real import
  used. "Keep both" and "Merge" are asserted as the bytes sent to beets and
  have not been watched against a real library.
- **The starvation message.** The condition is reproduced from a transcript in
  a test, not by starving a real beets.

## Debt this release did not clear

- Issue #28: re-labelling checks the track count but not the order, so a
  release with the same tracks in a different sequence passes the guard and
  mis-titles silently. This release's record is exactly that shape; it was
  avoided by not re-labelling, not by the guard.
- Nothing checks that a cut and its pinned release agree before the import
  runs. That mismatch is what produced every symptom here.
- Issue #24: installing artwork resets the tracks to 0600.
- Issue #19: an oversized body desyncs a keep-alive connection.
- The trim ADR-036 promised, still owed.
